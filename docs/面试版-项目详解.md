# 智析 RAG（ZuoAI-Agent）— 面试详解版

## 项目背景

基于 Spring AI + PgVector 构建企业级 RAG（检索增强生成）对话系统。
核心目标：让用户用自然语言向企业私有知识库提问，系统自动检索相关文档后结合 LLM 给出准确回答。

**技术栈**：Spring Boot 3.4 / Spring AI 1.0 / PostgreSQL + pgvector / MyBatis-Plus / Ollama / DashScope / SiliconFlow

---

## 整体流水线

```
用户提问
  → ① 查询改写（补全语义）
  → ② 意图分类（确定检索目标）
  → ③ 多通道并行检索（向量召回）
  → ④ LLM 重排序（精选 Top-3）
  → ⑤ Prompt 组装（注入上下文）
  → ⑥ 路由流式推送（SSE 输出）
```

每个阶段异步写入 `t_rag_trace_run` / `t_rag_trace_node` 追踪表，记录耗时与输入输出，支持完整链路回溯。

## 模块详解

### ① 多通道并行检索

**问题**：单一全局向量检索语义覆盖不足，召回噪声多。

**实现**（`MultiChannelRetriever`）：
- 基于 `CompletableFuture` 同时发起两条通路：
  - **全局通道**：在全量向量空间检索，覆盖面广
  - **意图定向通道**：按 `kb_id` 过滤，仅检索目标知识库，精度高
- 意图置信度 < 0.5 时仅走全局通道（`kbId=null`，定向通道返回空列表）
- 设置 10s 超时，超时后降级为仅全局检索
- 合并规则：意图定向结果在前，全局结果补充，按 `document.id` 去重

**关键代码位置**：`rag/MultiChannelRetriever.java`

**面试问**：为什么不只用一个通道？
> 全局通道召回率高但精度低；意图定向精度高但依赖分类准确性。两者互补，意图分类不准时全局兜底，保证召回不遗漏。

### ② Chat / Embedding 双维熔断路由

**问题**：单一 AI 模型服务不稳定，宕机时整个服务不可用。

**Chat 熔断实现**（`ChatCircuitBreaker` + `RoutingChatService`）：
- 每个候选模型独立维护三态熔断器，存于 `ConcurrentHashMap`
- 状态转换：
  - `CLOSED`：正常，允许调用
  - `OPEN`：连续失败达阈值（默认 2 次）后熔断，拒绝调用
  - `HALF_OPEN`：OPEN 持续超过 30s 后转入，放行一个探测请求
  - 探测成功 → 回 CLOSED；探测失败 → 重回 OPEN
- **首包探测机制**（`RoutingChatService.tryStreamWithEntry`）：
  - 流式接口无法从 HTTP 状态码判断成功，需等到第一个 SSE chunk 才能确认
  - 用 `CompletableFuture<Boolean>` 监听首个 chunk，10s 内未收到视为失败
  - 触发候选切换，避免将错误流发送给用户

**Embedding 熔断实现**（`CircuitBreakerEmbeddingModel` + `EmbeddingModelFactory`）：
- 候选列表存于 `ArrayDeque` 队列，按 priority 排序
- `poll()` 取队头，调用成功/失败后 `offerTail()` 放回队尾
- 实现了 Spring AI `EmbeddingModel` 接口，直接替换 `PgVectorStore` 的默认 EmbeddingModel

**重要约束**：Embedding 熔断路由要求所有启用候选必须是同模型族、同维度，否则写入与查询向量空间不兼容。当前配置：ollama-qwen3 与 siliconflow-qwen3 均为 Qwen3-Embedding-8B（4096 维），可安全切换。

**面试问**：Chat 熔断和 Embedding 熔断有什么区别？
> Chat 可以随意在不同模型间切换，只要接口兼容；Embedding 切换有硬约束——维度和语义空间必须一致，否则写入的向量和查询的向量无法比较，检索结果完全错乱。

**关键代码位置**：`chat/ChatCircuitBreaker.java`、`chat/RoutingChatService.java`、`knowledge/embedding/CircuitBreakerEmbeddingModel.java`

### ③ 意图树三级分类

**问题**：用户问题五花八门，直接全库检索噪声大、耗时长。

**实现**（`IntentClassifier` + `IntentTreeService`）：
- 意图树结构：领域（root）→ 类目（category）→ 话题（topic），三级层次存于数据库
- 启动时加载到内存，定时刷新（默认 5 分钟）
- 分类流程：将意图树文本拼入 Prompt，让 LLM 返回对应节点的 ID（整数）
- 返回 `-1` 表示闲聊/系统节点，执行短路处理直接回复，跳过向量检索
- 返回有效节点 ID 时，置信度设为 0.85，将 `kbId` 传入多通道检索的定向通道
- 解析失败/异常时静默降级返回 `IntentResult.unknown()`，流水线继续全局检索

**面试问**：意图置信度是怎么计算的？
> 当前版本是规则型：LLM 成功返回合法节点 ID 时固定置信度 0.85，返回 -1（闲聊）或解析失败则为 0。置信度 >= 0.5 时才启用定向通道，低于阈值仅走全局检索。

**关键代码位置**：`intent/service/IntentClassifier.java`、`intent/service/IntentTreeService.java`

### ④ 查询改写

**问题**：多轮对话中用户常用指代词（"它"、"上面那个"），向量检索无法理解指代关系。

**实现**（`QueryRewriter`）：
- 改写前：「它的价格是多少？」→ 改写后：「XX 产品的价格是多少？」
- 通过 Prompt 模板（`prompts/query-rewrite.st`）让 LLM 将问题扩写为语义完整的独立查询
- 改写失败时静默回退原始 Prompt，不阻断流水线

**面试问**：改写和不改写有什么差别？
> 不改写时向量化的是"它的价格是多少"，向量语义极弱，几乎检索不到相关文档；改写后向量化完整问题，检索效果显著提升。

**关键代码位置**：`rag/QueryRewriter.java`、`prompts/query-rewrite.st`

---

### ⑤ LLM 重排序

**问题**：向量余弦相似度只衡量表面语义接近度，无法准确判断文档对问题的实际回答价值。

**实现**（`DocumentReranker`）：
- 检索召回 6 个文档后，用 LLM 对每个文档与问题的相关性打分（0~10 分）
- 每次打分独立调用 LLM（串行），文档内容截断至 800 字，避免超出 Token 限制
- 按分数降序取 Top-3 注入最终 Prompt
- 打分失败赋默认分 0，排在末尾

**面试问**：为什么不用专用 Rerank 模型？
> 成本考量，当前版本用 LLM 实现简单 Rerank，生产级可替换为 bge-reranker 等专用模型，接口已预留。

**关键代码位置**：`rag/DocumentReranker.java`

### ⑥ 持久化对话记忆与摘要压缩

**问题**：内存记忆重启丢失；历史消息过多导致 Token 超限，每轮都传全量历史成本高。

**实现**（`DbBasedChatMemory`）：
- 对话消息存入 PostgreSQL `t_chat_memory` 表，按 `conversation_id` 隔离
- **滑动窗口**：`get()` 时只取最近 20 条（`historyKeep=20`）注入上下文
- **摘要压缩**：每次写入后检查该会话消息总数，超过 `summaryStartTurns * 2`（默认 20 条）时触发：
  1. 取最旧的一半消息 ID
  2. 调用 LLM 生成不超过 200 字的摘要
  3. 删除原始消息，写入 `role=system` 的摘要消息
- 压缩失败只打 warn 日志，不影响主流程

**面试问**：为什么用摘要而不是直接删除旧消息？
> 直接删除会丢失重要历史背景（如用户自我介绍、之前设定的条件等），摘要保留了关键语义，在 Token 可控的前提下维持了对话连贯性。

**关键代码位置**：`chatmemory/DbBasedChatMemory.java`

### ⑦ 全链路追踪

**实现**（`RagTraceRecordService`）：
- 每次流水线调用生成 UUID `traceId`，写入 `t_rag_trace_run`（run 级别）
- 流水线 5 个阶段（改写/分类/检索/重排/Prompt组装）各写一条 `t_rag_trace_node`
- 记录内容：阶段名、状态（RUNNING/SUCCESS/ERROR）、耗时（ms）、输入 JSON、输出 JSON（含检索文档内容）
- 全部写库操作加 `@Async`，异步执行，不阻塞流水线主线程

**实际价值**：
- 定位性能瓶颈：哪个阶段耗时最长
- 分析 RAG 效果：查看实际检索到了哪些文档片段
- 故障排查：快速找到哪个节点 `status=ERROR`

**关键代码位置**：`trace/service/impl/RagTraceRecordServiceImpl.java`

## 常见面试追问

**Q：RAG 和普通 LLM 问答的区别？**
> 普通 LLM 基于训练数据回答，无法获取私有/实时知识，且可能幻觉。RAG 先检索私有文档，将相关内容注入 Prompt，LLM 基于检索结果作答，可溯源、可更新。

**Q：向量检索的原理？**
> 将文档和问题分别通过 Embedding 模型转为高维向量，存入 PgVector（HNSW 近似最近邻索引），检索时计算查询向量与所有文档向量的余弦相似度，取 Top-K 最相似的文档。

**Q：PgVector 为什么用 HNSW 索引？**
> HNSW（Hierarchical Navigable Small World）是近似最近邻算法，相比精确扫描（Flat）检索速度快数十倍，精度损失极小（recall > 95%），适合生产环境大规模向量检索。当前维度配置为 4096（Qwen3-Embedding-8B），余弦距离。

**Q：意图分类失败了怎么办？**
> 静默降级返回 `IntentResult.unknown()`，置信度为 0，流水线跳过定向通道只走全局检索，保证对话不中断。

**Q：熔断的 HALF_OPEN 有什么用？**
> OPEN 状态直接拒绝所有请求，但模型可能已经恢复。HALF_OPEN 是一个探测窗口——放行一个请求试探，成功则全面恢复，失败则重新熔断，避免频繁无效切换。
