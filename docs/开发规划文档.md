## 一、Situation（背景/现状）

### 1.1 项目现状

`zuo-ai-agent` 是一个 Spring Boot 3.4 + Spring AI 1.x + Java 17 + PostgreSQL 17(pgvector) 的 AI Agent 项目，已具备以下核心能力：

- 多候选 Chat/Embedding 模型路由与熔断
- 知识库 CRUD + 文档入库流水线（分块→增强→向量化→存储）
- 智能 RAG 管道（查询改写→意图分类→多通道检索→重排序→生成）
- 对话记忆（DB/文件/内存三种存储，10 轮后自动摘要压缩）
- RAG 执行全链路追踪（`t_rag_trace_run`/`t_rag_trace_node`）

### 2.2 领域模型（租户 → 团队 → 知识库 三层）

```
t_tenant（企业/组织）
  │
  ├── t_user（用户，N:N 归属团队）
  │     └── t_user_team（用户-团队关联表）
  │
  ├── t_team（部门/项目组）← 新增
  │     ├── t_user_team（团队成员）
  │     └── t_knowledge_base（知识库挂在团队下）
  │           ├── owner_id（默认 created_by，支持移交到用户/团队）
  │           └── t_knowledge_base_access（授权表，grantee_type: ALL/TEAM/USER）
  │
  └── t_role（角色，scope_type: TENANT/TEAM）
```

### 2.3 权限模型（RBAC + DataScope）

```
┌──────────┐     ┌──────────┐     ┌──────────────┐
│   User   │────→│   Role   │────→│  Permission   │
│  用户    │ N:N │  角色    │ N:N │  权限点        │
└────┬─────┘     └────┬─────┘     └──────────────┘
     │                │
     │         ┌──────┴──────┐
     │         │  DataScope  │  ← 数据范围
     │         │  - GLOBAL   │     平台管理员看全平台
     │         │  - TENANT   │     租户管理员看本租户
     │         │  - TEAM     │     团队管理员看本团队
     │         │  - SELF     │     普通用户看自己
     │         └─────────────┘
     │
     └────→ t_team（用户归属团队，N:N）
```

### 2.4 审批模型（统一审批表）

```
t_approval（一张表承载所有审批类型）
  apply_type:      TENANT_CREATE / ROLE_APPLY / KB_ACCESS / TEAM_JOIN / DOC_ACCESS
  approver_type:   PLATFORM_ADMIN / RESOURCE_OWNER / TEAM_ADMIN
  → 平台资源（租户/角色）→ 平台管理员审批
  → 私有资源（知识库/团队）→ 资源 owner 审批
```

### 2.5 资源授权模型（通用，支持未来扩展）

```
t_resource_access（通用资源授权表）
  resource_type:  KNOWLEDGE_BASE / DOCUMENT / FOLDER / ...（预留扩展）
  resource_id:    具体资源 ID
  grantee_type:   ALL / TENANT / TEAM / USER
  grantee_id:     被授权方 ID
  permission:     READ / WRITE / ADMIN
```

### Phase 1：知识库入库 + 对话记忆 Redis 化 + RabbitMQ 引入

**目标**：修复正确性问题，落地入库异步化、MD5 去重、Redis 对话记忆新架构，引入 RabbitMQ 作为异步消息中间件。

**前提条件**：Phase 0 完成。

**产出**：RabbitMQ + Redis 基础设施（Phase 2 Sa-Token 会话持久化复用 Redis）、对话记忆表结构（Phase 2 补充 `tenant_id`）。

**RabbitMQ 设计**：

```
Exchange: zuo.ai.agent (Topic)
  ├── Queue: ingestion.queue
  │     Routing Key: zuo.ai.agent.ingestion
  │     用途：文档入库（分段→Embedding→向量化→更新状态）
  │     消费者：IngestionConsumer（zuo-ai-agent 内部）
  │     特性：手动 ACK + 死信队列（DLX）+ 重试 3 次
  │
  ├── Queue: chat.memory.persistence.queue
  │     Routing Key: zuo.ai.agent.chat.memory.persistence
  │     用途：对话消息异步持久化（Redis 消息 → MySQL 双表落盘）
  │     消费者：ChatMemoryPersistenceConsumer（zuo-ai-agent 内部）
  │     特性：手动 ACK + 死信队列（DLX）+ 重试 3 次
  │
  └── Queue: chat.memory.compression.queue
        Routing Key: zuo.ai.agent.chat.memory.compression
        用途：对话历史异步压缩（队列超阈值 → 异步 LLM 摘要 → 回填 Redis）
        消费者：ChatMemoryCompressionConsumer（zuo-ai-agent 内部）
        特性：手动 ACK + tryLock 放弃 + 死信队列（DLX）+ 重试 3 次
```

**入库流水线（业界标准模式）**：

```
上传接口（生产者）               RabbitMQ                 消费者 Worker
     │                            │                           │
     │ 1. 同步落库(status=pending)  │                           │
     │ 2. 发送到 ingestion.queue   │                           │
     │────────────────────────────→│                           │
     │ 3. 返回 docId+status        │                           │
     │                            │ 4. 消费消息                │
     │                            │───────────────────────────→│
     │                            │                           │ 5. 分段
     │                            │                           │ 6. Embedding
     │                            │                           │ 7. 写入向量库
     │                            │                           │ 8. 更新 status=success
     │                            │                           │ 9. 手动 ACK
     │                            │                           │
     │                            │ 失败：重试3次→DLX→更新    │
     │                            │ status=failed + 记录原因   │
```

**对话记忆（双队列异步模式）**：

```
add() 流程（极简，不阻塞用户）：
     │
     │ 1. LPUSH 消息到 Redis List
     │ 2. LLEN 检查队列长度
     │     ├── 超阈值 → 发送 MQ 压缩消息
     │     └── 未超 → 跳过
     │ 3. 发送 MQ 持久化消息
     │ 4. 立即返回 ✅
     │
     ▼
 CompressionConsumer（异步压缩）：
     │
     │ 1. 收到消息 {conversationId, 快照msgIds}
     │ 2. tryLock(0) → 失败？ACK（跳过）
     │ 3. 读取队尾消息，与快照比对
     │ 4. 不一致？ACK（已处理）
     │ 5. 调用 LLM 生成摘要                         ← 异步，用户无感知
     │ 6. Lua 脚本原子执行：移除旧消息 + 回填摘要
     │ 7. 释放锁 → ACK
     │
     ▼
 PersistenceConsumer（异步持久化）：
     │
     │ 1. 收到消息 {msgId, conversationId, role, content}
     │ 2. 写入 MySQL t_chat_message_raw
     │ 3. ACK
```

**时序图**：

```
用户发消息    add()      Redis    MQ(压缩)   MQ(持久化)  CompressionConsumer
     │          │          │         │          │              │
     │─────────→│          │         │          │              │
     │          │─LPUSH───→│         │          │              │
     │          │─LLEN────→│         │          │              │
     │          │          │         │          │              │
     │          │ 超阈值？─发送────→│          │              │
     │          │          │         │          │              │
     │          │──────────│─────────发送─────→│              │
     │          │          │         │          │              │
     │←─返回────│          │         │          │              │
     │          │          │         │          │              │
     │  （用户无感知）       │         │          │              │
     │          │          │         │          │              │
     │          │          │         │          │─消费─────────→│
     │          │          │         │          │              │─tryLock
     │          │          │         │          │              │─校验快照
     │          │          │         │          │              │─LLM摘要
     │          │          │         │          │              │─Lua回填
     │          │          │         │          │              │
     │ 下次 get() 时，压缩摘要已就绪 ✅                          │
```

| ARCH-02 | 知识库 owner | 默认 `created_by`，支持移交到用户/团队 |
| ARCH-03 | MD5 去重 | 业务层按团队提示 + 存储层全局去重，用户决定 |
| ARCH-04 | 对话记忆隔离 | 按租户隔离，不按团队共享 |
| ARCH-05 | 授权粒度 | 知识库级别，不做文档级 |
| ARCH-06 | 前端布局 | 参考 Dify 风格（侧边栏+顶部导航） |
| ARCH-07 | RBAC 架构 | 拆分为独立 auth-service 微服务 |
| ARCH-08 | 权限模型 | RBAC + DataScope 四级 + 权限点注册 + 审计 + 统一审批表 |
| ARCH-09 | 资源授权 | 通用 `t_resource_access` 表，`resource_type` 预留 DOCUMENT 扩展 |
| ARCH-10 | log-monitor-service | 独立微服务，日志查看/搜索 + 监控打点/告警 + 基础设施监控面板 |
| ARCH-11 | 数据库/缓存 | 不做独立中间件服务，改为监控面板采集指标 |
| ARCH-12 | 不做项 | 文档级授权、独立 DB/Cache 中间件、自动故障转移 |
| ARCH-13 | 异步方案 | RabbitMQ，Topic Exchange + 三个 Queue（ingestion / persistence / compression）+ DLX 死信队列，docker-compose 本地部署 |
| ARCH-14 | 存储矩阵 | 知识库向量→PGVector，知识库全文→PG tsvector，应用日志→ES，对话记忆→Redis(热)+PG(冷)，业务数据→PG |
| ARCH-15 | 限流框架 | Sentinel，各服务接入 Sentinel 控制台，支持 QPS/线程数/熔断降级 |
